## 1. ✅ Ограничить разрешение рендера в Meadow

**Это самый дешёвый выигрыш из всех найденных.**

### Проблема

Пляж и Луг по-разному вычисляют масштаб канваса.

`prototype/flat.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality, 0.75);
```

`prototype/meadow.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality);
```

Разница — третье слагаемое `0.75`. На этой машине `devicePixelRatio = 2`, `P.quality = 2`, поэтому:

| Тема | Масштаб | Канвас | Пикселей |
|---|---:|---|---:|
| Пляж | 0.75 | 1920×1080 | 2.07 М |
| Луг | 2.0 | 5120×2880 | 14.75 М |

**Луг рисует в 7.1 раза больше пикселей, чем Пляж.**

### Замер

Внутренний бенчмарк сцены (`window.__dbg.bench()`, медиана из 10 кадров, offscreen 2560×1440):

```text
flat.html            frame 10 мс   canvas 1920×1080
meadow.html          frame 48 мс   canvas 5120×2880
meadow.html + 0.75   frame 24 мс   canvas 1920×1080
```

Живой замер слоя (сумма `themehost.py` + `WebKitWebProcess`, 12 с):

| Тема | Одно ядро |
|---|---:|
| Пляж | 41.4% |
| Ночь | 49.7% |
| Луг | **62.2%** |

### Исправление

Перенести ограничение из `flat.html` в `meadow.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality, 0.75);
```

### Ожидаемый эффект

Кадр: 48 → 24 мс. Живой CPU: ориентировочно 62% → 45%.

Разница в качестве не видна: сцена — размытый фон под иконками, мелкие детали в облаках и траве на глаз неразличимы, а WebKit всё равно масштабирует канвас на весь экран.

### Замечание

Это же ограничение стоит применить и в `night.html` — там оно уже есть (`dpr` ограничен единицей), но по другой причине. Стоит унифицировать формулировку во всех трёх файлах и упомянуть в `THEMES.md` как требование к новой теме, а не как личную находку.

## 2. ✅ Дебаунс перестроек при перетаскивании иконок

### Проблема

`themehost.py` опрашивает иконки раз в 2 секунды и при любом изменении сразу отправляет их странице:

```python
if payload != self.last_icons:
    self.last_icons = payload
    self.send(payload)
```

Страница на это немедленно вызывает `commit()`, который пересчитывает поле расстояний:

```js
function commit(fromEmpty = false) {
  const nf = computeField(iconRects());
  // …
}
```

### Замер

`computeField()` при 11 иконках на 2560×1440, шаг сетки 5 px, 149 060 узлов:

```text
28.9 мс на вызов
```

Бюджет кадра при 30 fps — 33 мс. То есть один пересчёт — это почти целый кадр, выброшенный целиком.

При перетаскивании иконки `gio` обновляет позицию много раз подряд, и каждый раз это ещё 29 мс. Отсюда рывки при drag&drop.

### Как это решено у Wololand

```rust
// Debounce: a file being written to the desktop, or icons being dragged, changes the
// layout many times in a row; build once it settles instead of on every change.
if self.read_icons() {
    self.build_due = Some(now + Duration::from_millis(700));
}
```

### Исправление

В `themehost.py`: не отправлять сразу, а завести отложенную отправку.

```python
def poll_icons(self):
    rects = iconsource.collect()
    payload = ...
    if payload == self.last_icons:
        return True
    self.last_icons = payload
    if self._icons_timer is not None:
        GLib.source_remove(self._icons_timer)
    self._icons_timer = GLib.timeout_add(700, self._flush_icons)
    return True

def _flush_icons(self):
    self._icons_timer = None
    self.send(self.last_icons)
    return False
```

Отдельно: при смене темы и при первом `ready` задержку надо обходить — там важна немедленная реакция.

### Ожидаемый эффект

При спокойном столе — ничего не меняется (событий нет). При перетаскивании — одна перестройка вместо десятка. Субъективно это самое заметное улучшение из списка.

## 3. ✅ Понизить приоритет слоя

### Проблема

Сцена конкурирует с приложениями на равных. Если пользователь запустит сборку или игру, WebKit будет отбирать у неё кванты.

### Проверка

```bash
grep -rn "nice\|ionice\|setpriority" *.py *.sh
# (ничего)
```

### Как это решено у Wololand

```rust
// A wallpaper should never compete with apps.
SetPriorityClass(GetCurrentProcess(), BELOW_NORMAL_PRIORITY_CLASS);
// и для потока сборки:
SetThreadPriority(GetCurrentThread(), THREAD_MODE_BACKGROUND_BEGIN);
```

### Исправление

В `themehost.py`, сразу после старта:

```python
import os
try:
    os.nice(10)          # CPU: уступаем всем
except Exception:
    pass
```

В `start-layer.sh` — заодно понизить приоритет ввода-вывода:

```bash
setsid ionice -c3 nice -n 10 python3 "$DIR/themehost.py" ... &
```

`ionice -c3` — класс idle, диск трогается только когда он свободен.

### Ожидаемый эффект

В простое — ноль. Под нагрузкой — сцена уступает, а не делит поровну. Это ровно то поведение, которого ждёшь от обоев.

### Риск

При слишком агрессивном `nice` сцена может «задумываться» при перерисовке на слабой машине. `-n 10` — безопасная середина; при проблемах откатить до `-n 5`.

## 4. ✅ Пауза по площади покрытия

### Проблема

`themehost.py` ставит сцену на паузу только при `_NET_WM_STATE_MAXIMIZED_HORZ + _NET_WM_STATE_MAXIMIZED_VERT` или `_NET_WM_STATE_FULLSCREEN`.

Окно, растянутое вручную на 95% экрана, паузу не включает — сцена продолжает молотить CPU под почти невидимым рабочим столом.

### Как это решено у Wololand

```rust
let covers = r.left <= s.left && r.top <= s.top && r.right >= s.right && r.bottom >= s.bottom;
// a window covering nearly all of the screen hides the wallpaper too
let covers = covers || iw * ih * 100 >= area * 92;
let on_primary = cx >= s.left && cx < s.right && cy >= s.top && cy < s.bottom;
on_primary && (covers || IsZoomed(fg))
```

Плюс проверка `DWMWA_CLOAKED` — окно может быть «видимым», но скрытым композитором.

### Исправление

В `_should_pause()` добавить геометрическую проверку через `xwininfo`:

```python
geom = subprocess.run(["xwininfo", "-id", wid], capture_output=True, text=True).stdout
# Width: 2560  Height: 1440  Absolute upper-left X: 0  ...
```

Считать пересечение с геометрией монитора и включать паузу при покрытии ≥ 92%. Порог 92% взят у Wololand не из религии: он оставляет запас на док, панель задач и тени, чтобы обычное окно «почти на весь экран» не считалось полноэкранным.

### Ожидаемый эффект

Закрывает реальную дыру. На этой машине пауза срабатывает только на настоящий fullscreen; ручное растягивание — нет.

### Стоимость

Один дополнительный вызов `xwininfo` (1.7 мс) раз в секунду, и только когда окно уже maximized/fullscreen — то есть почти никогда.

## 5. ✅ RNG-потоки по назначению

### Проблема

`seed` в `flat.html` один на всё:

```js
let seed = (Math.random() * 1e6) | 0;
```

Он используется и для шума поля (`buildNoise`), и для позиций пальм, и для каяков, и для чаек. Любое изменение, сдвигающее порядок вызовов, меняет всю сцену — даже если изменилась одна иконка.

### Как это решено у Wololand

```rust
// One random stream per purpose: adding or moving an icon then only changes what is near it,
// instead of shifting every random choice made after it (islands, piles, buildings...).
let stream = |k: u64| Rng::new(seed ^ k.wrapping_mul(0x9e37_79b9_7f4a_7c15));
// дальше: stream(1) для островов, stream(2) для деревьев, …
```

### Исправление

Завести в странице несколько независимых ГПСЧ:

```js
const rng = (salt) => mulberry32((seed ^ Math.imul(salt, 0x9e3779b9)) >>> 0);
const rngPalms = rng(1), rngKayaks = rng(2), rngBirds = rng(3);
```

### Сделано (15.11.2026)

Замеры подтвердили проблему и показали два разных механизма:

**Пляж, пальмы.** В `beach-palms.js` место дерева выбиралось резервуарной
выборкой (`if (random() < 1 / ++candidates)`). Число вызовов ГПСЧ зависело
от того, сколько кандидатов прошло проверку, а проверка зависит от иконок —
сдвиг одной иконки переставлял все деревья. Заменено на выбор по весу
точки: `palmWeight(x, y, salt)` — хеш от координат и seed. Вес точки не
зависит от порядка обхода.

Проверка: пальмы `[[461,236],[567,275]]` оставались на месте при
добавлении и удалении иконки в другом углу экрана.

**Луг, облака.** `makeSkyCloud()` использовала `Math.random`, поэтому
каждое пересоздание давало другую форму. Облака при той же раскладке
получались `[629,264] → [122,293] → [556,269]`. Теперь форма выводится из
`mulberry32` с зерном от позиции облака и общего seed:
`(seed ^ 0x5c10d) + Math.imul(x, 2654435761)`.

Проверка: `[[756,168],[229,626],[1249,483]]` не менялись между тремя
прогонами.

**Что не потребовало правок.** В `night.html` потоки уже были раздельные
(четыре независимых `mulberry32`). Пляжные каяки и чайки тоже стабильны:
их начальные позиции берутся из `Math.random` один раз при spawn, а не
пересчитываются при каждой смене иконок.

### Ожидаемый эффект

Сейчас: подвинул иконку → перегенерировалась вся карта. После: изменилось только то, что рядом с иконкой.

Это не про CPU, это про восприятие: пользователь перетаскивает ярлык и не ждёт, что пустыня переедет на другое место.

### Риск

Средний: правка затрагивает порядок вызовов в нескольких местах. Нужно проверить, что после неё сцена выглядит так же при том же seed.

## 6. ✅ Ротация лога и health-строка

### Проблема

`run/wall.log` растёт без ограничений (сейчас 4 261 байт, но за недели работы это мегабайты). В нём только отладочные сообщения, по которым нельзя понять, течёт ли память.

### Как это решено у Wololand

```rust
if std::fs::metadata(&path).is_ok_and(|m| m.len() > 256 * 1024) {
    let _ = std::fs::remove_file(&path);
}
```

Раз в 10 минут:

```rust
format!("health: private {} MB, working set {} MB, handles {handles}, gdi {gdi}, user {user}", …)
```

### Исправление

В `themehost.py`:

```python
def _rotate_log(self):
    try:
        if (RUN / "wall.log").stat().st_size > 256 * 1024:
            (RUN / "wall.log").unlink()
    except Exception:
        pass
```

Раз в 10 минут писать строку:

```text
health: rss 167 МБ, потоков 8, uptime 3ч12м
```

RSS берётся из `/proc/self/status` (`VmRSS`).

### Ожидаемый эффект

Лог не растёт. Появляется возможность заметить утечку на длинном прогоне, а не гадать.

### Замечание

Наш общий RSS сейчас — **~530 МБ** (166 `themehost` + 301 `WebKitWebProcess` + 50 `WebKitNetworkProcess`). У Wololand по README — ~140 МБ. Часть разницы — неизбежная цена WebKit, но 301 МБ в web-процессе при одной статичной сцене выглядят завышенными. Health-лог покажет, растут ли они со временем.

## 7. ✅ Хуки `__renderAt` и `__inject` в Пляж и Луг

### Проблема

`tools/capture-theme.py`, `tools/test-theme.py` и `tools/bench-theme.py` требуют от страницы двух вещей:

- `?freeze=1` — не запускать `requestAnimationFrame`;
- `window.__renderAt(t)` — нарисовать кадр на момент `t`;
- `window.__inject(msg)` — доставить сообщение хоста (для тестов).

Есть это только в `night.html`. Для Пляжа и Луга инструменты печатают `SKIP`.

### Следствие

- GIF-превью для Пляжа и Луга записаны вручную и не воспроизводятся;
- контракт этих тем не проверяется автоматически;
- бенчмарк по эффектам к ним неприменим.

### Исправление

Добавить в `flat.html` и `meadow.html` по три строки:

```js
window.__renderAt = function (t) { draw(t); };
window.__inject = handle;   // имя функции-обработчика в каждой теме своё
```

И в конце инициализации:

```js
if (QS.has('freeze')) { draw(performance.now()); } else { scheduleFrame(); }
```

### Ожидаемый эффект

Инструменты начинают работать на всех трёх темах. Это не производительность, это качество процесса: любая новая тема сразу проверяема.

## 8. ⬜ Запекание статичной части сцены

**Главный пункт по эффекту. И самый рискованный.**

### Проблема

`flat.html` и `meadow.html` считают полноэкранный шейдер каждый кадр. Между кадрами меняются только:

- вода (волны, блики);
- юниты (пальмы качаются, каяки плывут, чайки летят, мальчик бежит);
- морфинг берега при изменении иконок.

Всё остальное — берег, песок, мокрый песок, трава, тени облаков — статично.

### Оценка разрыва

Пересчёт на равные условия с Wololand (их 3–4% при 1920×1080/15 fps, наши 41–62% при 2560×1440/30 fps):

| | Wololand | Mintland |
|---|---:|---:|
| Пикселей | 2.07 М | 3.69 М |
| Кадров/с | 15 | 30 |
| Относительная работа | 1.0 | 3.6 |
| Заявленный CPU | 3–4% | 41–62% |
| В пересчёте на их условия | 3–4% | **11–17%** |

Разрыв **в 3–5 раз**. Он не в шейдере — он в том, что мы перерисовываем неизменное.

### Возможное решение

Двухслойная схема:

1. **Статичный слой.** Берег, песок, трава, статичные тени — запекаются в текстуру при изменении иконок/параметров. Для Пляжа это уже почти есть: `computeField()` даёт поле, `uploadField()` заливает его в текстуру. Остаётся запечь и результат шейдера.
2. **Живой слой.** Вода, юниты, морфинг — рисуются каждый кадр поверх.

Морфинг берега — отдельная сложность: при перетаскивании иконки статичный слой нужно пересчитывать, но это происходит редко и как раз допускает паузу в один-два кадра.

### Ожидаемый эффект

По аналогии с Wololand — падение с 41–62% до примерно 10–20% одного ядра. Точнее предсказать нельзя без прототипа.

### Риск

Высокий:

- WebGL-сцена перестаёт быть «одним шейдером», появляется вторая текстура и логика её инвалидации;
- при HiDPI и смене размера окна текстуру нужно пересоздавать;
- `night.html` на canvas 2D уже делает нечто похожее (кэш неба), но Пляж и Луг — нет.

Поэтому это отдельная работа на 2–4 дня, а не правка на вечер. Начинать с прототипа на `flat.html`, замерять, и только потом решать.

### Что сделать до неё

Пункты 1–7. Они дешевле, безопаснее и уже дают ощутимый результат. Если после них CPU устроит — пункт 8 можно отложить.

## 9. ⛔ Тема-пресет рядом с темой-страницей

### Проблема

Сейчас тема — это отдельная HTML-страница. Три темы занимают 3 212 строк, то есть ~1 071 строк на тему. Каждая реализует протокол, работу с `devicePixelRatio` и обработку `pause` заново.

В `themes.json` при этом уже лежат 11 «запертых» тем из Deskland, из которых как минимум четыре — вариации существующих сцен (Мальдивы — это Пляж с другой палитрой).

Если добавлять их копированием, получится около 15 тысяч строк почти
одинакового кода.

### Как это устроено у Wololand

Десять тем — один `scene.rs` на 1 399 строк. Тема задаётся таблицами текстур и спрайтов плюс парой веток в общих функциях.

### Предложение

Не переписывать существующее, а ввести два уровня и зафиксировать их в `THEMES.md`:

| Уровень | Что | Когда |
|---|---|---|
| **Тема-страница** | Отдельный HTML по контракту | Принципиально иная механика (canvas 2D как `night.html`) |
| **Тема-пресет** | Таблица параметров над общей сценой | Вариация существующей: палитра, плотность, набор объектов |

Минимальный вариант: вынести в `flat.html` палитру и набор элементов в объект-пресет, а страницу сделать одну на несколько `id`. Тогда Мальдивы — это `flat.html?preset=maldives`, а не копия файла.

### Смежное направление

Отдельно стоит держать в виду [`PAPER.md`](PAPER.md): объектное семейство тем
(«карта на бумаге») сразу проектируется как один движок плюс таблицы
параметров. Если оно пойдёт в работу, оно и станет тем общим движком, о
котором говорит этот пункт, — и заводить его надо с чистой страницы, а не
переписыванием Пляжа.

### Чего пресеты НЕ дают: они не ускоряют загрузку

Это стоит зафиксировать отдельно, потому что напрашивается неверный вывод.
Замеры на этой машине (2560×1440, offscreen):

| Что | Время |
|---|---:|
| Холодный старт темы (первая загрузка) | **869 мс** |
| Переключение темы сейчас (перезагрузка страницы) | 236–453 мс |
| Смена параметров в живой странице (как на пресетах) | **1–19 мс** |

Отсюда видно главное: **холодный старт пресеты не ускоряют**. 869 мс — это
WebKit поднимает процесс, создаёт WebGL-контекст и компилирует шейдеры.
Сколько бы тем ни было описано таблицами, первый запуск останется таким же.

Пресеты ускоряют только **переключение между уже загруженными темами**, и то,
что там 20–200-кратная разница, на практике мало что значит: тему меняют
раз в день, а не каждую минуту. Если когда-нибудь понадобится быстрый холодный
старт — это отдельная задача (кэш страницы, предзагрузка в фоне), и пресеты
её не решают.

### Зачем тогда пресеты: масштабирование

Единственная, но решающая причина — стоимость **следующей** темы.

| | Значение |
|---|---|
| Три темы сейчас | 3 212 строк |
| В среднем на тему | ~1 071 строки |
| «Запертых» тем в реестре | 11 |
| Если каждую делать копией | **~14 993 строк** |

Пятнадцать тысяч строк, в которых протокол, `devicePixelRatio` и обработка
`pause` повторены одиннадцать раз. Ошибка в одном месте не чинится в
остальных десяти.

Пресеты превращают новую тему из «скопируй тысячу строк» в «добавь двадцать
строк таблицы». Это не про секунды, а про то, останется ли десять тем
мечтой или станет работой на неделю.

### Сделано: механизм есть, пресетов не прибавилось

Реализован первый уровень — палитра вынесена из шейдера в uniforms, добавлена
таблица `PALETTES` в `flat.html` и два способа выбрать пресет: параметр
`?preset=…` в адресе страницы и поле `palette` в параметрах темы, которое
`switcher.py` берёт из `preset` в `themes.json`. Переключение пресета не
перезагружает страницу: в логе одна запись `loading file` вместо двух.

Проверено замером среднего цвета моря на одном и том же кадре:
`beach` — `#0292bd`, `maldives` — `#12b4c1`, `lagoon` — `#0d519a`.

Проверено, что **вид Пляжа не изменился**: `beach` — это прежние цвета,
просто перенесённые в таблицу.

Но когда я добавил две темы-пресета (Мальдивы и Лагуну), выяснилось, что
они **выглядят как Пляж**. Замер подтвердил: отличаются только цвета.

| | Пляж | Мальдивы | Лагуна |
|---|---|---|---|
| вода вдали | `#008fba` | `#12b2bf` | `#0d4f99` |
| сухой песок | `#f7ede0` | `#fcf7eb` | `#edebe3` |
| разница песка от Пляжа | — | 12/441 | **11/441** |

Разница в песке — около 3%, это неразличимо. Даже после добавления разных
геометрических параметров (у Мальдив отмель шире, у Лагуны берег изрезаннее)
силуэт остаётся тем же: та же линия берега, те же пальмы, те же каяки.

Поэтому обе темы убраны из списка. В реестре снова три темы, и это честнее,
чем пять карточек, три из которых — один и тот же пляж в разных цветах.

**Вывод для будущих тем-пресетов:** палитры недостаточно. Чтобы вариант
читался как отдельная тема, он должен менять **форму**: силуэт берега,
набор объектов, композицию. Иначе это не тема, а цветовая схема.

### Чем всё закончилось: механизм отменён

Позже выяснилось, что и это не решение. Пресет как **отдельная запись в
реестре** встаёт рядом с исходной темой: `switcher.py` рисует по карточке
на каждую готовую запись, вложенности нет. Пять карточек, две из которых —
варианты соседних, хуже трёх честных.

Поэтому механизм заменён на **варианты внутри карточки** (§11 в этом плане,
§14 в `THEMES.md`): одна карточка, переключатель внутри неё, список тем не
растёт. Поле `preset` из реестра убрано, `switcher.py` его больше не читает.

Полезная часть первого этапа осталась: **палитра, вынесенная из шейдера в
uniforms**. Теперь она живёт в таблице `VARIANTS` каждой темы — у всех трёх
одинаково, включая Луг, где раньше цвета были зашиты константами.

### Ожидаемый эффект

Новая вариация существующей темы — не 1 000 строк, а 20. Это меняет экономику: десять тем становятся реальной целью, а не мечтой.

### Риск

Средний: затрагивает `themes.json`, `switcher.py` и сами страницы. Делать после того, как уляжется пункт 8, а не одновременно с ним.

## 10. ✅ Слежение за живостью `nemo-desktop`

### Проблема

Слой работает только если `nemo-desktop` жив и держит роль рабочего стола. `wall-on.sh` проверяет это при запуске:

```bash
if ! pgrep -x nemo-desktop >/dev/null; then
    say "nemo-desktop не запущен — иконки не рисуются."
```

Но если `nemo-desktop` упадёт **после** включения слоя, никто этого не заметит: сцена продолжит работать, а иконок не будет. Пользователь увидит красивые обои без ярлыков и не поймёт, что случилось.

### Как это решено у Wololand

```rust
pub enum AttachState {
    Ok,
    Gone,       // окно уничтожено (Explorer перезапустился)
    Detached,   // окно есть, но уже не ребёнок рабочего стола
}
```

Раз в 400 мс проверяется состояние, и при `Gone`/`Detached` приложение переприкрепляется.

### Исправление

В `themehost.py` раз в 5 секунд:

```python
if not subprocess.run(["pgrep", "-x", "nemo-desktop"], capture_output=True).returncode == 0:
    self._log("nemo-desktop пропал — иконки не рисуются")
    # и уведомление один раз, а не каждые 5 секунд
```

Плюс флаг, чтобы `notify-send` не спамил.

### Ожидаемый эффект

Пользователь узнаёт о проблеме сразу и понимает, что делать, вместо того чтобы искать причину.

§9), а запекание встроить в него сразу — оно там уместно, потому что
сборка сцены в этом движке уже будет отдельным этапом.

## 14. ✅ Вариант внутри карточки, а не отдельная тема

### Проблема

Первые два пресета (Мальдивы, Лагуна) были сделаны отдельными записями в
`themes.json`. `switcher.py` строит список так:

```python
themes = [t for t in data["themes"] if t.get("status") == "ready"]
for theme in self.themes:
    self.theme_box.pack_start(self._make_theme_card(theme), ...)
```

Каждая готовая запись — отдельная карточка, вложенности нет. Поэтому пресет
вставал рядом с исходной темой как равный, и в списке из трёх тем появлялось
пять карточек, две из которых — варианты соседних.

### Решение

Вариант живёт **внутри** карточки. У темы в реестре появляются два поля:

```json
"variants": [
  { "id": "polar", "name": "Полярная", "desc": "Сияние, луна и холодные холмы" },
  { "id": "fireflies", "name": "Светлячки", "desc": "Тёплый горизонт, рой светлячков над полем" }
],
"defaultVariant": "polar"
```

`theme_defaults()` добавляет `variant` к параметрам темы, `switcher.py`
рисует переключатель первым блоком в панели параметров, а страница получает
`variant` обычным сообщением `settings`.

```
[ Пляж ]   [ Луг ]   [ Ночь ]
                     └ Вариант: Полярная | Светлячки
```

Список тем не растёт: три карточки, как и было.

### Чем вариант отличается от набора ползунков

Это главное. Если вариант — только другие значения существующих ползунков,
пользователь соберёт его сам, и тема не нужна.

Поэтому вариант задаёт то, чего ползунками не достичь: **своё небо и свои
холмы**. В `night.html` появилась таблица `VARIANTS`:

| | Полярная | Светлячки |
|---|---|---|
| небо у горизонта | `#173152` холодный синий | `#5a4a34` тёплый оливковый |
| холмы | синие каменные | зеленоватые травянистые |
| сияние | 0.7 | 0 |
| луна | есть | нет |
| светлячки | 0 | 40 |

Небо — не ползунок: градиент задаётся только в таблице вариантов, поэтому
«Светлячки» нельзя повторить, покрутив настройки.

### Светлячки

Новый слой, ~60 строк. Каждый живёт в своей области над холмами и ходит по
замкнутой кривой: две синусоиды с несоизмеримыми периодами дают
неповторяющийся, но плавный путь. Яркость тоже дышит, у каждого свой ритм —
рой не мигает в такт. Рисуются в режиме `lighter`, между туманом и ореолами
иконок, чтобы не заслонять подписи.

Положение хранится долями от кадра, поэтому при смене размера окна рой
пересобирается и точки остаются на своих местах.

### Проверено

- переключатель появился: «Вариант · Полярная | Светлячки»;
- клик по «Светлячкам» меняет `variant` в состоянии, пишет его в
  `control.json`, страница получает `fireflies`;
- «Полярная» отрисована и совпадает с прежней Ночью;
- `test-theme.py` — 6/6 на всех трёх темах.

### Что осталось

Второй вариант для Луга. Механизм общий, но `meadow.html` палитру в
`VARIANTS` ещё не вынес — там цвета зашиты в шейдер.

## 15. ✅ Английский интерфейс и документация

### Проблема

Сейчас всё на русском: подписи в `switcher.py`, `THEMES.md`, `README.md`,
комментарии в коде. Пользователь вне русскоязычной среды не разберётся.

### Предложение

Два независимых уровня, их не надо смешивать:

| Что | Как | Зачем |
|---|---|---|
| Интерфейс | `i18n/ru.json` и `en.json` плюс переключатель в окне | человеку, который запустил программу |
| Документация | `README.en.md`, `docs/en/` | тому, кто читает репозиторий |

Для интерфейса: словарь строк и функция `t(key)`; язык берётся из
`LANG`, переопределяется вручную и запоминается в настройках. Уже есть
готовый образец — `settings.html`, который был удалён как мёртвый код; его
`loadLang`/`localizeRegistry` можно взять за основу (файл есть в истории,
коммит `4b1ede9`).

### Подводные камни

- **Ширина.** Немецкий и английский текст длиннее русского: кнопки и
  подписи поедут. Проверять скриншотом, а не на глаз.
- **Плюрализация.** «1 светлячок / 2 светлячка / 5 светлячков» в общем
  словаре не выразить одной строкой; нужна форма с числом.
- **Документация разъедется.** Два языка надо обновлять вместе, иначе
  английский отстанет на несколько коммитов. Либо генерировать, либо
  держать английский коротким (только установка и контракт).

### Стоимость

Интерфейс — 1–2 дня. Документация — 1–2 дня на перевод и ещё столько же
на поддержку в актуальном виде.

### Сделано

**Интерфейс.** Все подписи `switcher.py` собраны в словарь `UI` с ключами
`ru` и `en`; читаются через `t(lang, key)`. Названия тем, описания, группы,
подписи параметров, варианты и единицы переводятся через `theme_text`,
`param_text`, `group_text`, `variant_text` — русский текст по-прежнему
лежит в `themes.json`, чтобы был один источник. Переключатель языка — в
строке состояния; выбор хранится в `~/.config/mintland/lang`, без него язык
берётся из `LANG` и по умолчанию остаётся русским.

Найдено и исправлено при проверке: подпись «Слой продолжает работать после
закрытия окна» и заголовок «Тема» были локальными переменными и при смене
языка оставались русскими. Теперь это поля окна.

**Документация.** `README.en.md` — полный перевод README, файлы ссылаются
друг на друга. `docs/en/` — все семь документов плюс индекс, 3 577 строк.
Проверено структурой, а не на глаз: число заголовков, код-блоков и строк
таблиц совпадает с оригиналами у каждого файла.

Русский остаётся языком разработки: строки в `themes.json`, комментарии в
коде и исходные документы — русские. Английский добавлен рядом.

## 16. ⬜ Сборка `.deb`

### Зачем

Сейчас установка — это клон репозитория, `pip install pygobject`, компиляция
`deskwall.c` и правка `.desktop` руками. Для конечного пользователя это
неприемлемо.

`.deb` даёт: ставится двойным щелчком, зависимости подтягиваются сами,
файлы ложатся по стандартным путям, удаление чистое.

### Это разумно, да

Проект уже к этому готов лучше, чем кажется:

| Что нужно | Состояние |
|---|---|
| Зависимости выражены явно | `gi`, `webkit2gtk-4.1`, `libx11` — все из репозитория Mint |
| Нет сборки на месте | `deskwall.c` — единственный бинарник, 200 строк |
| Нет вендорных библиотек | всё системное |
| Конфиг в `~/.config` | уже так |

### Что понадобится

1. **`debian/`**: `control` (зависимости), `rules` (сборка `deskwall`),
   `install` (куда что кладётся), `postinst`/`prerm`.
2. **Пути.** Сейчас всё запускается из каталога проекта. В пакете код
   уедет в `/usr/share/mintland/`, настройки останутся в `~/.config/mintland/`.
   Значит, `HERE`/`PROTO` в `switcher.py` и `themehost.py` надо считать от
   расположения пакета, а не от текущего каталога.
3. **Запуск.** `.desktop` в `/usr/share/applications/`, иконка в
   `/usr/share/icons/`, автозапуск — опционально.
4. **Тема по умолчанию** при первом запуске и понятное сообщение, если
   сессия не X11.

### Риск

Средний. Главная ловушка — **пути**: если оставить их относительными,
пакет соберётся и даже запустится из папки, а после установки не найдёт
`prototype/`. Проверять надо на чистой машине или в контейнере, а не там,
где лежит исходник.

Второе: `nemo-desktop` и `deskwall` завязаны на Cinnamon/Muffin. В
`control` стоит указать `Recommends: cinnamon`, а в описании честно
написать, что поддерживается X11 и Cinnamon.

### Порядок

Логичнее после §15: пакет с интерфейсом на одном языке хуже, чем пакет с
двумя. И после §8 (запекание), потому что оно меняет структуру файлов
темы, а значит и то, что кладётся в пакет.

## 17. ⬜ Карты: один движок, четыре темы

### Что это

Четыре темы в `themes.json` сейчас заперты, и все четыре — карты:

| Тема | Что на ней |
|---|---|
| Город от руки | вид сверху на старый город: дома тушью, улицы, иконки на площадях |
| Цветной город | та же сетка улиц, но с красными крышами и цветными стенами |
| Старая карта | пергамент, материк, пунктирные дороги, повозки между городами |
| Морская карта | пергамент, порты, маяки, фарватеры, парусники |

Слово «семейство» здесь не про жанр — никаких «Природа / Фэнтези». Оно про
**техническое родство**: все четыре собираются одним кодом и различаются
таблицей — набором тайлов, плотностью застройки, палитрой.

### Чем карта отличается от нынешних тем

Все три нынешние темы устроены одинаково: у них есть **поле расстояний до
иконок**, и сцена к нему подстраивается.

- у Пляжа берег изгибается вокруг иконок, волны набегают по нормали;
- у Луга облака собираются в круги над иконками;
- у Ночи ореол светит вокруг каждой иконки.

То есть **иконки задают форму сцены**.

Карта работает наоборот: у неё **своя постоянная геометрия** — сетка улиц,
русло реки, линия берега. Она под иконки не подстраивается, а заранее
оставляет для них пустые места: площади, дворы, поляны. Здесь **сцена
задаёт места для иконок**.

Это переворот отношения «сцена ↔ иконки», и он требует другого кода, а не
другого шейдера.

### Что это значит на практике

| | Текущие темы | Карты |
|---|---|---|
| Отношение к иконкам | сцена деформируется вокруг | сцена постоянна, для иконок оставлены места |
| Основа | поле расстояний (SDF) | тайловая сетка плюс готовый рисунок |
| Новый код | шейдер | раскладка тайлов, поиск свободных мест |
| Движение | анимация поверх поля | объекты по расписанию: повозки, корабли, дым |

**Что остаётся общим.** Не только протокол (`icons`, `settings`,
`pause`, `ready`) — он общий для всех тем по определению. Общей остаётся и
вся обвязка вокруг сцены: чтение позиций иконок, обработка
`devicePixelRatio`, пауза по покрытию окна, инструменты `tools/`, запись
превью. Это и есть та часть, которую не надо писать заново.

**Что придётся написать.** Две вещи, и обе новые:

1. **Раскладка карты.** Нужно разложить сетку улиц так, чтобы в ней
   остались площадки под иконки конкретного пользователя. Проще всего —
   строить город вокруг известных позиций: где стоит иконка, там площадь,
   вокруг неё кварталы.
2. **Поиск свободного места.** Обратная задача: если иконку перетащили,
   найти ближайшую подходящую площадку, не ломая рисунок.

### Где это уже описано подробно

Этот пункт — только вводная. Полное техническое описание, включая выбор
изометрии, формат спрайтов, запекание статики и разбор лицензий, лежит в
[`PAPER.md`](PAPER.md).

Читать их надо вместе: `PAPER.md` отвечает на «как это устроить», а здесь —
только «почему это отдельный пункт плана и когда за него браться».

### Почему одним движком, а не четырьмя страницами

«Город от руки» и «Цветной город» — буквально одна сетка улиц в двух
стилях. Писать их двумя страницами значит дважды повторить раскладку,
поиск мест и отрисовку домов.

Движок плюс таблица даёт: новый стиль карты — это набор тайлов и палитра,
то есть десятки строк, а не тысяча.

### Как это связано с §9 и §14

Это ровно тот случай, о котором говорит §14 в `THEMES.md`: механика
принципиально другая, поэтому нужна **своя страница**, а не вариант
существующей.

Но урок §9 остаётся: движок надо писать сразу с таблицей параметров, иначе
четыре карты снова превратятся в четыре копии по тысяче строк.

### Когда браться

Не раньше, чем закрыт §8 (запекание): `PAPER.md` прямо на него опирается —
статика рисуется один раз в текстуру. Английский (§15) уже готов, так что
второе условие выполнено.

### Стоимость

1–2 недели на первый движок и одну карту, дальше по теме — день-два.

## 18. ✅ Тема «Лес»: деревья вместо заливок

### Что это

Новая готовая тема: вид сверху на лес. Земля — как в теме «Луг» (акварельные
заливки, штрихи травы, зерно бумаги), а поверх неё растут деревья. Вокруг
иконок — пустые поляны: там, где стоит иконка, деревья не растут.

Отличие от прежних трёх тем принципиальное: Пляж, Луг и Ночь рисуются
**заливкой** — поле расстояний до иконок и по нему считается цвет каждого
пикселя. Лес добавляет **объекты**: сотни отдельных деревьев, которые
рисуются поверх земли.

### Как сделано

**Деревья рисуются кодом**, а не берутся картинками. Причин две: они
произвольного размера и легко перекрашиваются, а лицензировать нечего.
Семь пород, три силуэта:

| Силуэт | Породы | Вид |
|---|---|---|
| `conifer` | ель, сосна, голубая ель | конус из наложенных ярусов хвои |
| `scallop` | дуб, берёза, ольха | крона-облако с волнистым краем и стволом |
| `spire` | тополь, кипарис | узкий высокий шпиль |
| `bush` | куст | низкая крона у земли |

**Слой отдельный от сцены.** Земля рисуется шейдером WebGL, деревья —
canvas 2D поверх. Так кроны выходят ровнее, чем в шейдере, и в слое не
приходится тащить шум земли.

**Плотность — шумом.** Деревья растут зарослями, а не ровным ковром: густота
задаётся бесшовным шумом (лес должен продолжаться за краями экрана, иначе
видна полоса обрыва).

**Поляны — по расстоянию до прямоугольников иконок.** Не по полю расстояний
темы «Луг»: то поле безразмерное (на иконке около −12, в стороне 300), и
порог в нём не переводится в пиксели наглядно.

### Анимация

Деревья уходят под землю и вырастают заново:

- иконка встала на место — деревья вокруг неё **уходят под землю** (рост
  уменьшается до нуля);
- иконку убрали — деревья **вырастают из-под земли** (рост 0 → 1);
- рост идёт ~0.8 с, уход быстрее.

У каждого дерева постоянный номер, поэтому при перестроении леса видно,
что именно изменилось.

### Производительность: перерисовывается только изменившееся

Это требовалось прямо: **то, что не меняется при перетаскивании иконки,
не перерисовывается.**

Слой деревьев живёт в закадровом холсте, на экран выводится готовый
результат одним `drawImage`. Когда часть леса меняется, перерисовывается
только прямоугольник вокруг изменившихся деревьев.

Замер: при перетаскивании иконки перерисовывается **9 участков общей
площадью 5.5% экрана**, а не всё изображение.

| Что | Время |
|---|---:|
| Земля (шейдер) | 0.5 мс |
| Слой деревьев (кэш) | 0.05 мс |
| Полный кадр | 4.6 мс |
| Перестроение леса | 1.2 мс |

### Проверено

- `test-theme.py` — 6/6 на всех четырёх темах;
- ползунки «Деревья» (0–900) и «Поляна» работают: `trees=50` → 50 деревьев,
  `trees=0` → пусто, `trees=220` → 220;
- на живом рабочем столе поляны вокруг иконок видны, иконки кликабельны.

### Ползунки

| Параметр | Диапазон | Что делает |
|---|---|---|
| Деревья | 0–900 | сколько деревьев в лесу |
| Поляна | 0–80 px | радиус вытоптанной земли вокруг иконки |
| Ореол вокруг иконок | 20–260 px | мягкое светлое пятно под иконкой |

**«Ореол» сначала не работал** — и это замечание было точным. Он брался
из поля расстояний, а то поле безразмерное: на самой иконке около 170, в
двухстах пикселях от неё — 320. Порог в таких числах почти не двигал
картинку. Теперь ореол и поляна считаются в пикселях от прямоугольника
иконки (uniform-массив `uIcon`), поэтому ползунок ведёт себя предсказуемо.

### Что осталось

Мальчика с воздушным змеем и кота в лесу нет — они остались в теме «Луг».
Для леса нужен свой набор персонажей или не нужен вовсе.
