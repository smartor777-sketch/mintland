## 1. Ограничить разрешение рендера в Meadow

**Это самый дешёвый выигрыш из всех найденных.**

### Проблема

Пляж и Луг по-разному вычисляют масштаб канваса.

`prototype/flat.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality, 0.75);
```

`prototype/meadow.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality);
```

Разница — третье слагаемое `0.75`. На этой машине `devicePixelRatio = 2`, `P.quality = 2`, поэтому:

| Тема | Масштаб | Канвас | Пикселей |
|---|---:|---|---:|
| Пляж | 0.75 | 1920×1080 | 2.07 М |
| Луг | 2.0 | 5120×2880 | 14.75 М |

**Луг рисует в 7.1 раза больше пикселей, чем Пляж.**

### Замер

Внутренний бенчмарк сцены (`window.__dbg.bench()`, медиана из 10 кадров, offscreen 2560×1440):

```text
flat.html            frame 10 мс   canvas 1920×1080
meadow.html          frame 48 мс   canvas 5120×2880
meadow.html + 0.75   frame 24 мс   canvas 1920×1080
```

Живой замер слоя (сумма `themehost.py` + `WebKitWebProcess`, 12 с):

| Тема | Одно ядро |
|---|---:|
| Пляж | 41.4% |
| Ночь | 49.7% |
| Луг | **62.2%** |

### Исправление

Перенести ограничение из `flat.html` в `meadow.html`:

```js
const scale = PREVIEW ? 0.45 : Math.min(devicePixelRatio || 1, P.quality, 0.75);
```

### Ожидаемый эффект

Кадр: 48 → 24 мс. Живой CPU: ориентировочно 62% → 45%.

Разница в качестве не видна: сцена — размытый фон под иконками, мелкие детали в облаках и траве на глаз неразличимы, а WebKit всё равно масштабирует канвас на весь экран.

### Замечание

Это же ограничение стоит применить и в `night.html` — там оно уже есть (`dpr` ограничен единицей), но по другой причине. Стоит унифицировать формулировку во всех трёх файлах и упомянуть в `THEMES.md` как требование к новой теме, а не как личную находку.

## 2. Дебаунс перестроек при перетаскивании иконок

### Проблема

`themehost.py` опрашивает иконки раз в 2 секунды и при любом изменении сразу отправляет их странице:

```python
if payload != self.last_icons:
    self.last_icons = payload
    self.send(payload)
```

Страница на это немедленно вызывает `commit()`, который пересчитывает поле расстояний:

```js
function commit(fromEmpty = false) {
  const nf = computeField(iconRects());
  // …
}
```

### Замер

`computeField()` при 11 иконках на 2560×1440, шаг сетки 5 px, 149 060 узлов:

```text
28.9 мс на вызов
```

Бюджет кадра при 30 fps — 33 мс. То есть один пересчёт — это почти целый кадр, выброшенный целиком.

При перетаскивании иконки `gio` обновляет позицию много раз подряд, и каждый раз это ещё 29 мс. Отсюда рывки при drag&drop.

### Как это решено у Wololand

```rust
// Debounce: a file being written to the desktop, or icons being dragged, changes the
// layout many times in a row; build once it settles instead of on every change.
if self.read_icons() {
    self.build_due = Some(now + Duration::from_millis(700));
}
```

### Исправление

В `themehost.py`: не отправлять сразу, а завести отложенную отправку.

```python
def poll_icons(self):
    rects = iconsource.collect()
    payload = ...
    if payload == self.last_icons:
        return True
    self.last_icons = payload
    if self._icons_timer is not None:
        GLib.source_remove(self._icons_timer)
    self._icons_timer = GLib.timeout_add(700, self._flush_icons)
    return True

def _flush_icons(self):
    self._icons_timer = None
    self.send(self.last_icons)
    return False
```

Отдельно: при смене темы и при первом `ready` задержку надо обходить — там важна немедленная реакция.

### Ожидаемый эффект

При спокойном столе — ничего не меняется (событий нет). При перетаскивании — одна перестройка вместо десятка. Субъективно это самое заметное улучшение из списка.

## 3. Понизить приоритет слоя

### Проблема

Сцена конкурирует с приложениями на равных. Если пользователь запустит сборку или игру, WebKit будет отбирать у неё кванты.

### Проверка

```bash
grep -rn "nice\|ionice\|setpriority" *.py *.sh
# (ничего)
```

### Как это решено у Wololand

```rust
// A wallpaper should never compete with apps.
SetPriorityClass(GetCurrentProcess(), BELOW_NORMAL_PRIORITY_CLASS);
// и для потока сборки:
SetThreadPriority(GetCurrentThread(), THREAD_MODE_BACKGROUND_BEGIN);
```

### Исправление

В `themehost.py`, сразу после старта:

```python
import os
try:
    os.nice(10)          # CPU: уступаем всем
except Exception:
    pass
```

В `start-layer.sh` — заодно понизить приоритет ввода-вывода:

```bash
setsid ionice -c3 nice -n 10 python3 "$DIR/themehost.py" ... &
```

`ionice -c3` — класс idle, диск трогается только когда он свободен.

### Ожидаемый эффект

В простое — ноль. Под нагрузкой — сцена уступает, а не делит поровну. Это ровно то поведение, которого ждёшь от обоев.

### Риск

При слишком агрессивном `nice` сцена может «задумываться» при перерисовке на слабой машине. `-n 10` — безопасная середина; при проблемах откатить до `-n 5`.

## 4. Пауза по площади покрытия

### Проблема

`themehost.py` ставит сцену на паузу только при `_NET_WM_STATE_MAXIMIZED_HORZ + _NET_WM_STATE_MAXIMIZED_VERT` или `_NET_WM_STATE_FULLSCREEN`.

Окно, растянутое вручную на 95% экрана, паузу не включает — сцена продолжает молотить CPU под почти невидимым рабочим столом.

### Как это решено у Wololand

```rust
let covers = r.left <= s.left && r.top <= s.top && r.right >= s.right && r.bottom >= s.bottom;
// a window covering nearly all of the screen hides the wallpaper too
let covers = covers || iw * ih * 100 >= area * 92;
let on_primary = cx >= s.left && cx < s.right && cy >= s.top && cy < s.bottom;
on_primary && (covers || IsZoomed(fg))
```

Плюс проверка `DWMWA_CLOAKED` — окно может быть «видимым», но скрытым композитором.

### Исправление

В `_should_pause()` добавить геометрическую проверку через `xwininfo`:

```python
geom = subprocess.run(["xwininfo", "-id", wid], capture_output=True, text=True).stdout
# Width: 2560  Height: 1440  Absolute upper-left X: 0  ...
```

Считать пересечение с геометрией монитора и включать паузу при покрытии ≥ 92%. Порог 92% взят у Wololand не из религии: он оставляет запас на док, панель задач и тени, чтобы обычное окно «почти на весь экран» не считалось полноэкранным.

### Ожидаемый эффект

Закрывает реальную дыру. На этой машине пауза срабатывает только на настоящий fullscreen; ручное растягивание — нет.

### Стоимость

Один дополнительный вызов `xwininfo` (1.7 мс) раз в секунду, и только когда окно уже maximized/fullscreen — то есть почти никогда.

## 5. RNG-потоки по назначению

### Проблема

`seed` в `flat.html` один на всё:

```js
let seed = (Math.random() * 1e6) | 0;
```

Он используется и для шума поля (`buildNoise`), и для позиций пальм, и для каяков, и для чаек. Любое изменение, сдвигающее порядок вызовов, меняет всю сцену — даже если изменилась одна иконка.

### Как это решено у Wololand

```rust
// One random stream per purpose: adding or moving an icon then only changes what is near it,
// instead of shifting every random choice made after it (islands, piles, buildings...).
let stream = |k: u64| Rng::new(seed ^ k.wrapping_mul(0x9e37_79b9_7f4a_7c15));
// дальше: stream(1) для островов, stream(2) для деревьев, …
```

### Исправление

Завести в странице несколько независимых ГПСЧ:

```js
const rng = (salt) => mulberry32((seed ^ Math.imul(salt, 0x9e3779b9)) >>> 0);
const rngPalms = rng(1), rngKayaks = rng(2), rngBirds = rng(3);
```

### Ожидаемый эффект

Сейчас: подвинул иконку → перегенерировалась вся карта. После: изменилось только то, что рядом с иконкой.

Это не про CPU, это про восприятие: пользователь перетаскивает ярлык и не ждёт, что пустыня переедет на другое место.

### Риск

Средний: правка затрагивает порядок вызовов в нескольких местах. Нужно проверить, что после неё сцена выглядит так же при том же seed.

## 6. Ротация лога и health-строка

### Проблема

`run/wall.log` растёт без ограничений (сейчас 4 261 байт, но за недели работы это мегабайты). В нём только отладочные сообщения, по которым нельзя понять, течёт ли память.

### Как это решено у Wololand

```rust
if std::fs::metadata(&path).is_ok_and(|m| m.len() > 256 * 1024) {
    let _ = std::fs::remove_file(&path);
}
```

Раз в 10 минут:

```rust
format!("health: private {} MB, working set {} MB, handles {handles}, gdi {gdi}, user {user}", …)
```

### Исправление

В `themehost.py`:

```python
def _rotate_log(self):
    try:
        if (RUN / "wall.log").stat().st_size > 256 * 1024:
            (RUN / "wall.log").unlink()
    except Exception:
        pass
```

Раз в 10 минут писать строку:

```text
health: rss 167 МБ, потоков 8, uptime 3ч12м
```

RSS берётся из `/proc/self/status` (`VmRSS`).

### Ожидаемый эффект

Лог не растёт. Появляется возможность заметить утечку на длинном прогоне, а не гадать.

### Замечание

Наш общий RSS сейчас — **~530 МБ** (166 `themehost` + 301 `WebKitWebProcess` + 50 `WebKitNetworkProcess`). У Wololand по README — ~140 МБ. Часть разницы — неизбежная цена WebKit, но 301 МБ в web-процессе при одной статичной сцене выглядят завышенными. Health-лог покажет, растут ли они со временем.

## 7. Хуки `__renderAt` и `__inject` в Пляж и Луг

### Проблема

`tools/capture-theme.py`, `tools/test-theme.py` и `tools/bench-theme.py` требуют от страницы двух вещей:

- `?freeze=1` — не запускать `requestAnimationFrame`;
- `window.__renderAt(t)` — нарисовать кадр на момент `t`;
- `window.__inject(msg)` — доставить сообщение хоста (для тестов).

Есть это только в `night.html`. Для Пляжа и Луга инструменты печатают `SKIP`.

### Следствие

- GIF-превью для Пляжа и Луга записаны вручную и не воспроизводятся;
- контракт этих тем не проверяется автоматически;
- бенчмарк по эффектам к ним неприменим.

### Исправление

Добавить в `flat.html` и `meadow.html` по три строки:

```js
window.__renderAt = function (t) { draw(t); };
window.__inject = handle;   // имя функции-обработчика в каждой теме своё
```

И в конце инициализации:

```js
if (QS.has('freeze')) { draw(performance.now()); } else { scheduleFrame(); }
```

### Ожидаемый эффект

Инструменты начинают работать на всех трёх темах. Это не производительность, это качество процесса: любая новая тема сразу проверяема.

## 8. Запекание статичной части сцены

**Главный пункт по эффекту. И самый рискованный.**

### Проблема

`flat.html` и `meadow.html` считают полноэкранный шейдер каждый кадр. Между кадрами меняются только:

- вода (волны, блики);
- юниты (пальмы качаются, каяки плывут, чайки летят, мальчик бежит);
- морфинг берега при изменении иконок.

Всё остальное — берег, песок, мокрый песок, трава, тени облаков — статично.

### Оценка разрыва

Пересчёт на равные условия с Wololand (их 3–4% при 1920×1080/15 fps, наши 41–62% при 2560×1440/30 fps):

| | Wololand | Mintland |
|---|---:|---:|
| Пикселей | 2.07 М | 3.69 М |
| Кадров/с | 15 | 30 |
| Относительная работа | 1.0 | 3.6 |
| Заявленный CPU | 3–4% | 41–62% |
| В пересчёте на их условия | 3–4% | **11–17%** |

Разрыв **в 3–5 раз**. Он не в шейдере — он в том, что мы перерисовываем неизменное.

### Возможное решение

Двухслойная схема:

1. **Статичный слой.** Берег, песок, трава, статичные тени — запекаются в текстуру при изменении иконок/параметров. Для Пляжа это уже почти есть: `computeField()` даёт поле, `uploadField()` заливает его в текстуру. Остаётся запечь и результат шейдера.
2. **Живой слой.** Вода, юниты, морфинг — рисуются каждый кадр поверх.

Морфинг берега — отдельная сложность: при перетаскивании иконки статичный слой нужно пересчитывать, но это происходит редко и как раз допускает паузу в один-два кадра.

### Ожидаемый эффект

По аналогии с Wololand — падение с 41–62% до примерно 10–20% одного ядра. Точнее предсказать нельзя без прототипа.

### Риск

Высокий:

- WebGL-сцена перестаёт быть «одним шейдером», появляется вторая текстура и логика её инвалидации;
- при HiDPI и смене размера окна текстуру нужно пересоздавать;
- `night.html` на canvas 2D уже делает нечто похожее (кэш неба), но Пляж и Луг — нет.

Поэтому это отдельная работа на 2–4 дня, а не правка на вечер. Начинать с прототипа на `flat.html`, замерять, и только потом решать.

### Что сделать до неё

Пункты 1–7. Они дешевле, безопаснее и уже дают ощутимый результат. Если после них CPU устроит — пункт 8 можно отложить.

## 9. Тема-пресет рядом с темой-страницей

### Проблема

Сейчас тема — это отдельная HTML-страница. Три темы занимают 3 803 строки, то есть ~1 270 строк на тему. Каждая реализует протокол, работу с `devicePixelRatio` и обработку `pause` заново.

В `themes.json` при этом уже лежат 11 «запертых» тем из Deskland, из которых как минимум четыре — вариации существующих сцен (Мальдивы — это Пляж с другой палитрой).

Если добавлять их копированием, получится 15 тысяч строк почти одинакового кода.

### Как это устроено у Wololand

Десять тем — один `scene.rs` на 1 399 строк. Тема задаётся таблицами текстур и спрайтов плюс парой веток в общих функциях.

### Предложение

Не переписывать существующее, а ввести два уровня и зафиксировать их в `THEMES.md`:

| Уровень | Что | Когда |
|---|---|---|
| **Тема-страница** | Отдельный HTML по контракту | Принципиально иная механика (canvas 2D как `night.html`) |
| **Тема-пресет** | Таблица параметров над общей сценой | Вариация существующей: палитра, плотность, набор объектов |

Минимальный вариант: вынести в `flat.html` палитру и набор элементов в объект-пресет, а страницу сделать одну на несколько `id`. Тогда Мальдивы — это `flat.html?preset=maldives`, а не копия файла.

### Смежное направление

Отдельно стоит держать в виду [`PAPER.md`](PAPER.md): объектное семейство тем
(«карта на бумаге») сразу проектируется как один движок плюс таблицы
параметров. Если оно пойдёт в работу, оно и станет тем общим движком, о
котором говорит этот пункт, — и заводить его надо с чистой страницы, а не
переписыванием Пляжа.

### Ожидаемый эффект

Новая вариация существующей темы — не 1 000 строк, а 20. Это меняет экономику: десять тем становятся реальной целью, а не мечтой.

### Риск

Средний: затрагивает `themes.json`, `switcher.py` и сами страницы. Делать после того, как уляжется пункт 8, а не одновременно с ним.

## 10. Слежение за живостью `nemo-desktop`

### Проблема

Слой работает только если `nemo-desktop` жив и держит роль рабочего стола. `wall-on.sh` проверяет это при запуске:

```bash
if ! pgrep -x nemo-desktop >/dev/null; then
    say "nemo-desktop не запущен — иконки не рисуются."
```

Но если `nemo-desktop` упадёт **после** включения слоя, никто этого не заметит: сцена продолжит работать, а иконок не будет. Пользователь увидит красивые обои без ярлыков и не поймёт, что случилось.

### Как это решено у Wololand

```rust
pub enum AttachState {
    Ok,
    Gone,       // окно уничтожено (Explorer перезапустился)
    Detached,   // окно есть, но уже не ребёнок рабочего стола
}
```

Раз в 400 мс проверяется состояние, и при `Gone`/`Detached` приложение переприкрепляется.

### Исправление

В `themehost.py` раз в 5 секунд:

```python
if not subprocess.run(["pgrep", "-x", "nemo-desktop"], capture_output=True).returncode == 0:
    self._log("nemo-desktop пропал — иконки не рисуются")
    # и уведомление один раз, а не каждые 5 секунд
```

Плюс флаг, чтобы `notify-send` не спамил.

### Ожидаемый эффект

Пользователь узнаёт о проблеме сразу и понимает, что делать, вместо того чтобы искать причину.

## 11. Порядок работ

## 12. Что замерить после каждого этапа

Чтобы не спорить о результатах на глаз:

```bash
# стоимость кадра темы (offscreen, без окна)
python3 tools/bench-theme.py prototype/night.html

# живой CPU слоя
python3 - <<'PY'
import time, os
pids=[]
for q in os.listdir('/proc'):
    if not q.isdigit(): continue
    try: cmd=open('/proc/%s/cmdline'%q,'rb').read().replace(b'\0',b' ').decode()
    except Exception: continue
    if 'themehost.py --html' in cmd or 'WebKitWebProcess' in cmd: pids.append(int(q))
def snap():
    t=0
    for p in pids:
        f=open('/proc/%d/stat'%p).read().split(); t+=int(f[13])+int(f[14])
    return t
a=snap(); t0=time.time(); time.sleep(12); b=snap()
print('%.1f%% одного ядра' % ((b-a)/os.sysconf('SC_CLK_TCK')/(time.time()-t0)*100))
PY

# память
for p in $(pgrep -f "themehost.py --html") $(pgrep -f WebKitWebProcess); do
    awk -v p=$p '/^VmRSS/{printf "%s: %d МБ\n", p, $2/1024}' /proc/$p/status
done
```

**Текущая точка отсчёта** (2560×1440, X11, живой слой):

| Тема | Одно ядро | RSS |
|---|---:|---:|
| Пляж | 41.4% | ~530 МБ |
| Луг | 62.2% | ~530 МБ |
| Ночь | 49.7% | ~530 МБ |

Проверять цикл вкл/выкл и иконки — по методике из `THEMES.md`, §9 («Проверка вживую»): снимок экрана ловит верхнее окно, поэтому сначала `wmctrl -k on`.

## 13. Чего в этом списке сознательно нет

- **Тем AoE2.** Требуют установленной платной игры и арта Microsoft. Не наш случай.
- **Порта Win32-кода.** `desktop.rs`, `overlay.rs`, `iconfx.rs` — 1 400 строк, неприменимых на Linux.
- **Полного переписывания на общий движок.** Убьёт работающее. Пункт 9 предлагает сосуществование, а не замену.
- **Своего рендера вместо WebKit.** Это отдельный проект на месяцы; текущая архитектура даёт приемлемый результат и уже отлажена.
