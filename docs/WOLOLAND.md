# Wololand: разбор чужого опыта

> **Документ:** технический анализ проекта [Wololand](https://github.com/gregstein/wololand) и оценка того, что из него применимо в Mintland.
> **Дата:** 14.11.2026.
> **Предмет:** какие архитектурные решения Wololand стоит перенять, какие неприменимы и почему.
> **Что это не так:** это не предложение портировать Wololand и не план работ. План — в `IMPROVEMENTS.md`.

---

## 0. Коротко

Wololand — живые обои для Windows, превращающие рабочий стол в карту Age of Empires II. Rust, MIT, 7 382 строки, создан 10.11.2026 (то есть исследован на третий день жизни проекта).

Ценность для Mintland не в темах и не в AoE2. Ценность в трёх вещах:

1. **Модель рендеринга.** Сцена запекается в одну текстуру при изменении иконок, а кадр — это блит текстуры плюс горстка спрайтов. У нас сцена пересчитывается каждый кадр.
2. **Тема как пресет, а не как отдельная программа.** Десять тем живут в одном файле и отличаются таблицами ресурсов и парой веток логики.
3. **Дисциплина по отношению к пользователю.** Понижение приоритета, дебаунс перестроек, лог с ротацией, пауза по площади покрытия. Это мелочи, которых у нас нет.

Отдельно важно: **ни один модуль Wololand, завязанный на Win32, переносу не подлежит.** Это 1 600 строк из 7 382. Переносится идея, а не код.

### 1.2. Лицензионная картина

Код — MIT, то есть может быть включён в GPL-3.0-проект с сохранением уведомления об авторстве.

Арт — **не MIT**. Спрайты и текстуры принадлежат Microsoft, и Wololand их не распространяет: он читает `.sld` и `.dds` из установленной копии игры в рантайме. Для нас это означает, что «темы AoE2 в Mintland» потребовали бы установленной AoE2 DE, то есть платной игры как зависимости обоев.

Настройки Wololand используют арт меню самой игры (пергамент, красные кнопки). Это нельзя копировать ни при какой лицензии кода.

## 2. Главная идея: запекание сцены

### 2.1. Как это работает у них

Из README:

> The map is baked into a single texture, so each frame only redraws the water and a handful of animated units.

Из `scene.rs`:

> The icon rectangles become a signed distance field (negative inside an icon cluster). Each theme turns that field plus some noise into terrain layers and object placement, all baked into one RGBA image on a background thread. Only that image and a handful of animated sprites are drawn per frame, which keeps the wallpaper cheap to run.

Три уровня стоимости:

| Работа | Когда происходит | Стоимость |
|---|---|---|
| Запекание карты | При изменении иконок, темы, размера окна | 200–300 мс на фоновом потоке |
| Блит текстуры + вода + спрайты | Каждый кадр | доли миллисекунды |
| Пересчёт поля расстояний | Внутри запекания | основная доля |

Итог по README: **3–4% одного ядра при 15 fps на 1920×1080**, ~140 МБ памяти.

### 2.2. Как это устроено у нас

`flat.html` и `meadow.html` считают всю сцену в WebGL-шейдере **каждый кадр**. Поле расстояний до иконок (`computeField`) пересчитывается только при изменениях, но всё остальное — вода, берег, песок, пена, градиенты — рисуется заново 30 раз в секунду.

`night.html` рисует canvas 2D: статичное небо кэшируется в отдельный canvas, сияние — в уменьшенный буфер с обновлением раз в 140 мс, ореолы и туман — каждый кадр.

Замеры на этой машине (2560×1440, живой слой, сумма `themehost.py` + `WebKitWebProcess`):

| Тема | Одно ядро | Доля от 20 потоков |
|---|---:|---:|
| Пляж (`flat.html`) | 41.4% | ~2.1% |
| Ночь (`night.html`) | 49.7% | ~2.5% |
| Луг (`meadow.html`) | 62.2% | ~3.1% |

Сравнивать с их «3–4%» напрямую нельзя: у них 1920×1080 при 15 fps, у нас 2560×1440 при 30 fps. Пересчёт на равные условия:

- пикселей у нас в 1.78 раза больше;
- кадров в 2 раза больше;
- итого работы в ~3.6 раза больше.

Их 3–4% × 3.6 ≈ **13% одного ядра**. У нас 41–62%. Разрыв — **в 3–5 раз**, и он не в «тяжёлом шейдере», а в том, что мы перерисовываем неизменное.

### 2.3. Что это значит

Сцена меняется только когда:

- пользователь перетащил иконку;
- добавился или удалился файл на рабочем столе;
- переключилась тема;
- изменились параметры из `switcher.py`;
- изменился размер экрана.

Всё остальное время — статичная картинка плюс несколько движущихся объектов. Пересчитывать её 30 раз в секунду — это трата, а не дизайн.

## 3. Вторая идея: тема как пресет

### 3.1. У них

Все десять тем описаны в одном `scene.rs`. Тема — это набор таблиц:

```rust
fn textures(self) -> &'static [&'static str] {
    match self {
        Theme::Arabia | Theme::GoldRush => &["g_gr3", "g_gr7", "g_gr4", "g_for", "g_des"],
        Theme::Arena | Theme::Hideout => &["g_gr2", "g_gr6", "g_fo2", "g_gr4", "g_grs"],
        Theme::BlackForest | Theme::ForestNothing => &["g_for", "g_fo2", "g_grs", "g_r01", "g_underbrush_leaves"],
        Theme::Islands => &["g_gr2", "g_gr6", "g_bch", "g_sh2"],
        // …
    }
}

fn sprites(self) -> Vec<&'static str> { /* то же самое */ }
```

Плюс несколько веток в общих функциях:

```rust
fn forest(&self, d: f32, n1: f32, n2: f32) -> f32 {
    match self.kit.theme {
        Theme::Arabia | Theme::Nomad => smoothstep(0.635, 0.66, n2) * smoothstep(140.0 * ds, 200.0 * ds, d),
        Theme::Arena | Theme::Hideout => { /* кольцо леса за стенами */ }
        Theme::BlackForest => { /* сплошной лес с просеками */ }
        Theme::ForestNothing => smoothstep(22.0 * ds, 52.0 * ds, d + (n1 - 0.5) * 40.0 * ds),
        // …
    }
}
```

Добавление темы — это строка в `enum Theme`, строка в `ALL`, две таблицы и одна ветка. Десять тем на 1 399 строк: **~140 строк на тему**, включая общий движок.

### 3.2. У нас

| Тема | Файл | Строк |
|---|---|---:|
| Пляж | `flat.html` + `beach-palms.js` | 1 292 + 159 |
| Луг | `meadow.html` + `meadow-boy.js` + `meadow-cat.js` | 1 141 + 531 + 101 |
| Ночь | `night.html` | 579 |

Три темы на 3 803 строки: **~1 270 строк на тему**. Каждая — самостоятельная программа со своим рендером, своим протоколом и своей обработкой `pause`.

Это не ошибка сама по себе: автономная страница проще для автора одной темы и не требует общего движка. Но у неё есть цена:

- три реализации протокола → три места, где можно забыть `pause`;
- три реализации `devicePixelRatio` → три разных поведения на HiDPI (см. `IMPROVEMENTS.md`, §1);
- три реализации `__renderAt` → `tools/capture-theme.py` работает только с `night.html`;
- новая тема = новый файл на тысячу строк, а не набор таблиц.

`night.html` это косвенно подтверждает: он в 2.2 раза короче `flat.html`, потому что проще по замыслу, а не потому что архитектура лучше.

### 3.3. Что из этого следует

Не «переписать всё на общий движок» — это уничтожит то, что уже работает. А зафиксировать в `THEMES.md` два уровня темы:

| Уровень | Что это | Когда выбирать |
|---|---|---|
| **Лёгкая тема** | Отдельная страница по контракту | Что-то принципиально иное: canvas 2D, другая механика |
| **Тема-пресет** | Таблица параметров над общим движком | Ещё одна вариация уже существующей сцены |

Пляж и Мальдивы в `themes.json` — это буквально одна сцена с разной палитрой. Сейчас для второй пришлось бы копировать 1 292 строки.

## 4. Третья идея: дисциплина по отношению к пользователю

Это набор мелочей, каждая из которых по отдельности незаметна, а вместе они дают ощущение «программа не мешает».

### 4.1. Потоки RNG по назначению

```rust
// One random stream per purpose: adding or moving an icon then only changes what is near it,
// instead of shifting every random choice made after it (islands, piles, buildings...).
let stream = |k: u64| Rng::new(seed ^ k.wrapping_mul(0x9e37_79b9_7f4a_7c15));
```

У нас `seed` глобальный: `flat.html` использует его и для шума поля, и для пальм, и для каяков. Подвинул иконку — потенциально изменилось всё.

### 4.2. Дебаунс перестроек

```rust
if self.read_icons() {
    self.build_due = Some(now + Duration::from_millis(700));
}
```

Комментарий объясняет: перетаскивание иконки или запись файла меняют раскладку десятки раз подряд; пересобирать надо один раз, когда всё успокоится.

У нас `themehost.py` шлёт новую раскладку сразу, а страница немедленно вызывает `commit()` → `computeField()`. Замер: **28.9 мс** на пересчёт поля при 11 иконках. При бюджете кадра 33 мс это заметный рывок, и при перетаскивании он повторяется многократно.

### 4.3. Приоритет

```rust
// A wallpaper should never compete with apps.
SetPriorityClass(GetCurrentProcess(), BELOW_NORMAL_PRIORITY_CLASS);
// для потока сборки:
SetThreadPriority(GetCurrentThread(), THREAD_MODE_BACKGROUND_BEGIN);
```

У нас нет ни `nice`, ни `ionice`. Сцена конкурирует с приложениями на равных.

### 4.4. Пауза по площади покрытия

```rust
let covers = r.left <= s.left && r.top <= s.top && r.right >= s.right && r.bottom >= s.bottom;
// a window covering nearly all of the screen hides the wallpaper too
let covers = covers || iw * ih * 100 >= area * 92;
```

Плюс проверка `DWMWA_CLOAKED` — окно может быть «видимым», но фактически скрытым композитором.

Наш `_should_pause()` требует именно `_NET_WM_STATE_MAXIMIZED` или `_NET_WM_STATE_FULLSCREEN`. Окно, растянутое вручную почти на весь экран, паузу не включит.

### 4.5. Лог с ротацией

```rust
if std::fs::metadata(&path).is_ok_and(|m| m.len() > 256 * 1024) {
    let _ = std::fs::remove_file(&path);
}
```

Раз в 10 минут в лог пишется строка о памяти, хендлах и GDI-объектах — чтобы утечку было видно на длинном прогоне.

У нас `run/wall.log` растёт без ограничений и содержит только отладочные сообщения.

### 4.6. Восстановление после падения оболочки

Если Explorer перезапустился, Wololand переприсоединяется за ~2 секунды: `attachment_state()` различает «окно уничтожено» и «окно отцепилось», и вызывающий код решает, пересоздавать или переприкреплять.

У нас `wall-on.sh` и `wall-off.sh` перезапускают `nemo-desktop`, но если `nemo-desktop` упадёт сам при работающем слое, никто этого не заметит.

## 5. Что переносится, а что нет

### 5.1. Переносится

| Идея | Где у них | Как у нас |
|---|---|---|
| Запекание сцены в текстуру | `scene.rs`, `app.rs` | Кэш кадра в `themehost.py` или в странице |
| Тема как пресет | `scene.rs` | Уровни темы в `THEMES.md` |
| RNG-потоки по назначению | `build()` | `seed ^ salt` на каждую задачу |
| Дебаунс перестроек | `app.rs` | Задержка в `themehost.py` перед отправкой `icons` |
| Понижение приоритета | `desktop.rs` | `os.nice()` + `ionice` |
| Пауза по площади | `desktop.rs` | Проверка геометрии активного окна |
| Ротация лога | `main.rs` | `run/wall.log` |
| Health-лог | `desktop.rs` | Раз в 10 минут в тот же лог |
| Изолинии поля | `contour_lines()`, `lay_wall()` | Новый класс тем: стены, заборы, набережные |

### 5.2. Не переносится

| Модуль | Строк | Причина |
|---|---:|---|
| `desktop.rs` | 424 | `Progman`, `WorkerW`, `SHELLDLL_DefView`, чтение памяти `explorer.exe` |
| `overlay.rs` | 318 | `UpdateLayeredWindow`, `WS_EX_TRANSPARENT`, `HTTRANSPARENT` |
| `iconfx.rs` | 662 | Layered-окна поверх иконок, скриншоты иконок |
| `tray.rs` | 190 | `Shell_NotifyIcon` |
| `aoe/` | 361 | SLD/DDS-декодеры — существуют только ради арта AoE2 |

Итого 1 955 строк из 7 382 — это Win32 и парсинг игровых форматов.

### 5.3. Отдельно: как они читают иконки

```rust
OpenProcess(PROCESS_VM_OPERATION | PROCESS_VM_READ | PROCESS_VM_WRITE, false, pid)
WriteProcessMemory(...)   // кладём в чужой процесс структуру RECT
SendMessageW(list, LVM_GETITEMRECT, ...)
ReadProcessMemory(...)    // забираем результат
```

Это чтение памяти чужого процесса (`explorer.exe`). Работает, но требует прав и выглядит грубо.

Наш `iconsource.py` читает gvfs-метаданные (`metadata::nemo-icon-position`) и `~/.config/nemo/desktop-metadata` — без доступа к чужой памяти. Это **не хуже**, это честнее.

### 5.4. Любопытная деталь

`overlay.rs` решает задачу «рисовать поверх иконки, но не перехватывать клики» через `WM_NCHITTEST → HTTRANSPARENT`. Это ровно наш «Шаг 9: передний кликопрозрачный слой» из дорожной карты. У нас есть `input_shape_combine_region` в `themehost.py`, то есть техника знакомая — но подтверждение, что подход рабочий, полезно.

## 6. Чему они научили на своих ошибках

В комментариях видно несколько мест, где авторы явно наступили на грабли и записали вывод:

**«Не двигать все WorkerW на каждое событие»**

```rust
// Only move the ones that are above: pushing each one to the very bottom on every call would
// make several WorkerWs swap places forever, each move firing another reorder event in Explorer.
```

Классический цикл обратной связи: своё же действие порождает событие, которое требует того же действия. У нас аналогичный риск есть в `_raise_nemo()`, который вызывается дважды после загрузки страницы.

**«Запоминать, что скриншот не удался»**

```rust
/// Failed screenshots, so a covered icon is not retried every frame.
tries: u32,
retry_at: f32,
```

Если операция может стабильно падать, её нельзя повторять в каждом кадре — нужен backoff.

**«Ограничение частоты исправлений»**

```rust
// Explorer fires these for every window it creates or moves; at most one fix per 50 ms
// (the 400 ms poll catches anything skipped).
```

Быстрый обработчик события + медленный опрос как страховка. Это ровно та схема, которая у нас есть в `poll_icons` (2 с) и которой не хватает для реакции на перетаскивание.

## 7. Где Wololand слабее нас

Чтобы картина не была односторонней.

| Аспект | Wololand | Mintland |
|---|---|---|
| Зависимость от платной игры | Обязательна | Нет |
| Платформа | Только Windows | Linux/X11 (Wayland в плане) |
| Чтение иконок | Через память чужого процесса | Через gvfs-метаданные |
| Прозрачность работы | Бинарник без исходной документации протокола | `THEMES.md` с контрактом |
| Инструменты для авторов тем | CLI `render`/`simulate`/`montage` | `capture`/`test`/`preview`/`bench` |
| Лицензия арта | Неопределима (арт Microsoft) | GPL-3.0 на всё, кроме ассетов Deskland |

Их CLI-инструменты, кстати, интереснее наших по замыслу: `render <theme> <out.png>` рисует сцену офлайн вокруг примерных иконок, `simulate <theme> [seconds]` прогоняет юнитов headless и печатает, что они делают. Наш `preview-frame.py` делает первое, но второго (прогона анимации без экрана) у нас нет.

## 8. Итог

**Что взять в первую очередь:** запекание сцены. Это единственное изменение, которое даёт выигрыш в разы, а не в проценты.

**Что взять попутно:** RNG-потоки, дебаунс, приоритет, пауза по площади, ротация лога. Каждое — маленькая правка, вместе — заметное изменение характера программы.

**Что взять как направление:** тема-пресет рядом с темой-страницей. Не переписывать существующее, а не плодить копии в будущем.

**Что не брать:** Win32, GPUI, DDS/SLD, AoE2 как зависимость, арт меню игры.

**Главный вывод, который бьёт по нашему `THEMES.md`:** мы объявили тему отдельной страницей на тысячу строк. Это работает для трёх тем. Для десяти — не работает. Wololand получает десять тем из 1 399 строк именно потому, что тема у них — данные, а не программа.
